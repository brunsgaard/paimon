# Kafka CDC

Consume change events from Kafka and write them into one Paimon table or route them to separate tables in a Paimon database.

See [CDC Action Configuration](./action-configuration) for command syntax, computed columns, and job settings,
and [Schema Evolution and Type Mapping](./schema-evolution) for shared behavior.

## Prerequisites {#prepare-kafka-bundled-jar}

Place the connector jar matching your Flink runtime in `<FLINK_HOME>/lib/`:

```text
flink-sql-connector-kafka-*.jar
```

## Supported Formats

Set the event format with `--kafka_conf value.format=<format>`. Paimon parses insert, update,
and delete events from the message value. Plain JSON represents insert-only data.

| `value.format` | Input |
| --- | --- |
| `canal-json` | Canal JSON change events |
| `debezium-json` | Debezium JSON change events; include the `schema` field for source types |
| `debezium-avro` | Debezium Avro using a Confluent schema registry; set `schema.registry.url` |
| `maxwell-json` | Maxwell JSON change events |
| `ogg-json` | Oracle GoldenGate JSON change events |
| `json` | Plain JSON records, treated as inserts |
| `aws-dms-json` | AWS Database Migration Service change events |
| `debezium-bson` | [MongoDB events captured by Debezium](./kafka-debezium-bson) |
| `protobuf` | Protobuf records decoded with a descriptor set, treated as inserts; set `protobuf.descriptor-set.path` and `protobuf.message-name` |

Check the event metadata before choosing a synchronization mode:

- Missing field types are mapped to `STRING`. Preserve the Debezium `schema` field when available.
- Database synchronization needs source database and table names to route records. Without these,
  use a table action and name the target explicitly.
- Missing primary keys can produce an append-only target. Supply `--primary_keys` when appropriate
  for update/delete events, and ensure the required key fields are present in those events.

## Synchronizing Tables

By using [KafkaSyncTableAction](https://paimon.apache.org/docs/master/api/java/org/apache/paimon/flink/action/cdc/kafka/KafkaSyncTableAction.html) in a Flink DataStream job or directly through `flink run`, users can synchronize one or multiple tables from Kafka's one topic into one Paimon table.

If the target does not exist, the action creates it from the first usable data record found during
schema discovery. It then evolves the schema as records arrive. For an existing target, it checks
schema compatibility before starting ingestion when source metadata is available.

### Example: ingest CDC events

This example assumes the source event contains `id` and `create_time`, and derives the `pt` partition:

```bash
<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-@@VERSION@@.jar \
    kafka_sync_table \
    --warehouse hdfs:///path/to/warehouse \
    --database test_db \
    --table test_table \
    --partition_keys pt \
    --primary_keys id,pt \
    --computed_column 'pt=date_format(create_time,yyyy-MM-dd)' \
    --kafka_conf properties.bootstrap.servers=127.0.0.1:9020 \
    --kafka_conf topic=order \
    --kafka_conf properties.group.id=123456 \
    --kafka_conf value.format=canal-json \
    --catalog_conf metastore=hive \
    --catalog_conf uri=thrift://hive-metastore:9083 \
    --table_conf bucket=4 \
    --table_conf changelog-producer=input \
    --table_conf sink.parallelism=4
```

### Start with an Empty Topic

If schema discovery cannot find a usable data record, create the target table first. Follow
[Starting with an Empty Topic](./action-configuration#starting-with-an-empty-topic), then submit
the table action with its source connection options.

### Example: ingest append-only JSON

Use `value.format=json` for records such as logs that contain only inserts. This example derives
`pt` from the source field `event_tm` and creates a table without primary keys.

```bash
<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-@@VERSION@@.jar \
    kafka_sync_table \
    --warehouse hdfs:///path/to/warehouse \
    --database test_db \
    --table test_table \
    --partition_keys pt \
    --computed_column 'pt=date_format(event_tm, yyyyMMdd)' \
    --kafka_conf properties.bootstrap.servers=127.0.0.1:9020 \
    --kafka_conf topic=test_log \
    --kafka_conf properties.group.id=123456 \
    --kafka_conf value.format=json \
    --catalog_conf metastore=hive \
    --catalog_conf uri=thrift://hive-metastore:9083 \
    --table_conf sink.parallelism=4
```

### Example: ingest protobuf

Use `value.format=protobuf` for records encoded with Protocol Buffers. The format needs no
generated classes. Point it at a serialized `FileDescriptorSet` and name the message type. Produce
the set with `protoc --descriptor_set_out=events.desc --include_imports events.proto` and put it
where the Flink cluster can read it.

```bash
<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-@@VERSION@@.jar \
    kafka_sync_table \
    --warehouse hdfs:///path/to/warehouse \
    --database test_db \
    --table purchases \
    --kafka_conf properties.bootstrap.servers=127.0.0.1:9020 \
    --kafka_conf topic=purchases \
    --kafka_conf properties.group.id=123456 \
    --kafka_conf value.format=protobuf \
    --kafka_conf protobuf.descriptor-set.path=s3://schemas/purchases.desc \
    --kafka_conf protobuf.message-name=com.example.Purchase \
    --kafka_conf protobuf.descriptor-set.refresh-interval=60s \
    --catalog_conf metastore=hive \
    --catalog_conf uri=thrift://hive-metastore:9083 \
    --table_conf sink.parallelism=4
```

Column types follow the message. Integers map to `INT` or `BIGINT`, `uint64` to `DECIMAL(20, 0)`,
`bytes` to `STRING` holding base64, enums to `STRING` holding the value name,
`google.protobuf.Timestamp` to `TIMESTAMP(6)` in UTC, nested messages to `ROW`, repeated fields to
`ARRAY` and map fields to `MAP`. Unset fields are `NULL` unless `protobuf.read-default-values` is
true.

When producers add fields to the message, publish the new descriptor set to the same path. With a
refresh interval set, the job picks it up and the schema evolution of the sink adds the columns.
Records written before the change hold `NULL` in the new columns. Records that already carry a
field the table does not have yet are written without it until the descriptor set is refreshed.

For `kafka_sync_database`, the format uses the topic name as both database and table name, because
protobuf messages carry neither. Rename targets with `--table_mapping`, `--table_prefix` or
`--table_suffix`.

#### Column comments and field identity

Every column the format creates carries a description of the form `<comment> [proto:<number>]`.
The comment is the field's leading comment from the descriptor set, present when it was written
with `protoc --include_source_info`, and the marker is the protobuf field number. Editing a comment
in the proto updates the column description on the next record.

The marker is what lets the sink follow the two changes it cannot see from names alone. Both are
table options, off by default.

| Table option | Effect |
| --- | --- |
| `cdc.schema-evolution.rename-by-comment=true` | A field with an unknown name whose marker matches a column the source no longer has is renamed, not added. The column keeps its field id, so history reads under the new name. Works inside nested messages too. |
| `cdc.schema-evolution.drop-missing-columns=true` | A column with a marker that the source no longer has is dropped, top-level or nested. Partition keys, primary keys and unmarked columns such as computed columns are never dropped. A column re-added later with the same name gets a new field id, so old files show `NULL` for it. |

Dropping is only safe with a format whose record schema is the complete schema derived from a
descriptor, which protobuf is. The action refuses the option for formats that derive the schema
from each record.

Type changes follow the usual rules. Widening such as `int32` to `int64` or `float` to `double`
updates the column type. Narrowing is ignored. A change protobuf itself cannot carry on the wire,
such as `int64` to `string`, fails the job until the descriptor is put back, and a producer still
on the old schema decodes to `NULL` for that field.

## Synchronizing Databases

By using [KafkaSyncDatabaseAction](https://paimon.apache.org/docs/master/api/java/org/apache/paimon/flink/action/cdc/kafka/KafkaSyncDatabaseAction.html) in a Flink DataStream job or directly through `flink run`, users can route source tables from one or more topics into a Paimon database.

The action uses a shared sink for the selected tables. It creates each missing target from that
source table's records and applies supported schema changes to existing targets. Source tables
without primary keys are also supported; choose target keys that match the event semantics.

### Example: route tables from one topic

```bash
<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-@@VERSION@@.jar \
    kafka_sync_database \
    --warehouse hdfs:///path/to/warehouse \
    --database test_db \
    --kafka_conf properties.bootstrap.servers=127.0.0.1:9020 \
    --kafka_conf topic=order \
    --kafka_conf properties.group.id=123456 \
    --kafka_conf value.format=canal-json \
    --catalog_conf metastore=hive \
    --catalog_conf uri=thrift://hive-metastore:9083 \
    --table_conf bucket=4 \
    --table_conf changelog-producer=input \
    --table_conf sink.parallelism=4
```

### Example: route tables from multiple topics

Separate topic names with semicolons and quote the argument so the shell passes it as one value.

```bash
<FLINK_HOME>/bin/flink run \
    /path/to/paimon-flink-action-@@VERSION@@.jar \
    kafka_sync_database \
    --warehouse hdfs:///path/to/warehouse \
    --database test_db \
    --kafka_conf properties.bootstrap.servers=127.0.0.1:9020 \
    --kafka_conf 'topic=order;logistic_order;user' \
    --kafka_conf properties.group.id=123456 \
    --kafka_conf value.format=canal-json \
    --catalog_conf metastore=hive \
    --catalog_conf uri=thrift://hive-metastore:9083 \
    --table_conf bucket=4 \
    --table_conf changelog-producer=input \
    --table_conf sink.parallelism=4
```

## Additional Kafka Configuration {#additional-kafka_config}

Pass these options through `--kafka_conf` in addition to the source connection settings:

| Option | Default | Description |
| --- | --- | --- |
| `schema.registry.url` | None | Confluent schema registry URL, required for `value.format=debezium-avro`. |
| `protobuf.descriptor-set.path` | None | Path to a serialized `FileDescriptorSet`, required for `value.format=protobuf`. Any file system Flink supports, for example `file:///`, `s3://` or `gs://`. |
| `protobuf.message-name` | None | Fully qualified message name, required for `value.format=protobuf`. |
| `protobuf.descriptor-set.refresh-interval` | 0 | How often to check the descriptor set for changes. Zero disables the check. |
| `protobuf.read-default-values` | false | Emit protobuf default values for unset fields instead of `NULL`. |

Two table options, passed with `--table_conf`, let the sink follow renames and deletions of
protobuf fields. See [Column comments and field identity](#column-comments-and-field-identity).

| Table option | Default | Description |
| --- | --- | --- |
| `cdc.schema-evolution.rename-by-comment` | false | Rename a column when a source field with a new name carries the same `[proto:N]` marker as a vanished column. |
| `cdc.schema-evolution.drop-missing-columns` | false | Drop marked columns the source no longer has. Only for formats that provide the complete schema, such as protobuf. |

## Debezium-bson

For MongoDB events captured by Debezium, use `value.format=debezium-bson`. See
[Kafka Debezium BSON Format](./kafka-debezium-bson) for full-document requirements, the Kafka key
fallback, and BSON-to-string conversion examples.
